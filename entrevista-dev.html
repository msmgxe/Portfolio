📐 UML — Los 5 Diagramas que más Preguntan

Un Jefe de Desarrollo valida que el AF sepa cuándo usar cada diagrama y qué información comunica al equipo técnico.

🎯 Pregunta típica: "¿Qué diagramas UML usas en tu día a día y para qué sirve cada uno? Dame un ejemplo concreto."
1️⃣ Diagrama de Casos de Uso — ¿Qué puede hacer el sistema?

Cuándo usarlo: Al inicio del proyecto para mostrar las funcionalidades al cliente y al equipo técnico sin entrar en detalles.

  • Actor: quien interactúa (cliente, admin, sistema externo)
  • Caso de uso: funcionalidad del sistema (elipse)
  • <<include>>: siempre se ejecuta junto
  • <<extend>>: extensión opcional
✅ Ejemplo Comsatel: Actor "Admin Corporativo" → caso de uso "Gestionar Líneas" <<include>> "Autenticar Usuario"
2️⃣ Diagrama de Secuencia — ¿Cómo fluye el mensaje?

Cuándo usarlo: Para explicar al equipo técnico el flujo de llamadas entre componentes. Esencial para diseñar APIs e integraciones.

  • Línea de vida: actor/componente vertical
  • Mensaje síncrono →: espera respuesta
  • Mensaje asíncrono --→: no espera
  • Fragmento alt/loop: condiciones y ciclos
💡 Para la entrevista: Siempre dibuja el happy path primero, luego menciona los flujos alternativos (error 401, timeout, datos no encontrados).
3️⃣ Diagrama de Actividad — ¿Cómo fluye el proceso?

Cuándo usarlo: Para modelar flujos de negocio complejos con decisiones. Similar al BPMN pero más técnico.

  • Inicio (●): punto de entrada
  • Actividad [□]: acción concreta
  • Decisión (◇): bifurcación con condiciones
  • Fork/Join (━━━): paralelismo
  • Fin (⊗): punto de salida
4️⃣ Diagrama de Clases — ¿Cómo está estructurado el sistema?

Cuándo usarlo: Para comunicar al equipo la estructura de datos del dominio. El AF lo crea con el arquitecto.

  • Clase: nombre + atributos + métodos
  • Herencia (▷): "es un"
  • Composición (◆): "parte de" (muere con el padre)
  • Asociación (─): "se relaciona con"
  • Multiplicidad: 1, *, 1..*, 0..1
5️⃣ Diagrama de Estados — ¿Cómo cambia el estado de un objeto?

Cuándo usarlo: Para modelar el ciclo de vida de una entidad del negocio (tickets, órdenes, líneas móviles).

  • Estado [ ]: situación de la entidad
  • Transición →: evento que cambia el estado
  • Guardia [cond]: condición para la transición
  • Acción /act: lo que ocurre al transitar
✅ Ejemplo Comsatel: Línea móvil → estados: Solicitada → Activa → Suspendida → Cancelada. Cada estado tiene reglas de negocio distintas.
✅ Tu experiencia: En AFP Profuturo usaste diagramas de secuencia para documentar la integración de tokenización PCI-DSS. En Perurail modelaste el flujo de reservas con diagramas de actividad en Bizagi/Visio. Menciona estos proyectos concretos.

✅ Definition of Ready (DoR)

Una historia está lista para el sprint si:

  • Está escrita en formato As a / I want / So that
  • Criterios de aceptación en formato Given/When/Then
  • Estimada por el equipo (Planning Poker)
  • Sin dependencias bloqueantes abiertas
  • Mockup o wireframe adjunto si aplica
  • No tiene ambigüedades (el equipo lo entiende solo)

✅ Definition of Done (DoD)

Una historia está terminada si:

  • Código revisado (code review aprobado)
  • Unit tests escritos y pasando
  • Tests de integración pasando
  • Desplegado en ambiente de pruebas
  • UAT validado por el AF/PO
  • Documentación técnica actualizada
  • Sin bugs Críticos o Altos abiertos

🔌 APIs REST — Lo que el Equipo Técnico espera que sepas

Como AF Senior, debes poder especificar endpoints, entender errores y colaborar con el equipo de integración sin depender de ellos para cada pregunta.

🎯 Pregunta típica: "¿Has trabajado con APIs? ¿Cómo documentas un endpoint para que el equipo pueda implementarlo?"

🔵 GET — Consultar

Obtiene datos. No modifica nada.

  • GET /api/lineas → lista todas
  • GET /api/lineas/987654321 → una línea
  • GET /api/lineas?estado=activa → filtrado

🟢 POST — Crear

Crea un nuevo recurso. Body con JSON.

  • POST /api/lineas → nueva línea
  • POST /api/sesion → login
  • POST /api/alertas → crear alerta

🟡 PUT/PATCH — Actualizar

PUT: reemplaza todo. PATCH: solo campos.

  • PUT /api/lineas/987 → actualiza completo
  • PATCH /api/lineas/987 → solo el plan

🔴 DELETE — Eliminar

Elimina o desactiva un recurso.

  • DELETE /api/lineas/987 → elimina
  • Generalmente se hace soft delete (estado=CANCELADA)

🗄 SQL — Consultas que todo AF Senior debe dominar

No necesitas ser DBA, pero sí debes poder escribir consultas para validar datos, verificar requisitos y crear reportes rápidos sin depender del equipo técnico.

🎯 Pregunta típica: "¿Has trabajado con SQL? ¿Puedes escribir una consulta para obtener las líneas con más del 80% de consumo?" — A veces te dan papel y lápiz.
1️⃣ SELECT básico — WHERE, ORDER BY, LIMIT
-- Líneas con consumo mayor al 80% del plan SELECT l.numero_linea, l.nombre_titular, l.plan_nombre, l.consumo_mb, l.limite_mb, ROUND((l.consumo_mb * 100.0 / l.limite_mb), 1) AS porcentaje_uso FROM lineas l WHERE l.estado = 'ACTIVA' AND l.consumo_mb > (l.limite_mb * 0.80) ORDER BY porcentaje_uso DESC LIMIT 10;
2️⃣ JOINs — La habilidad SQL más preguntada
INNER JOIN
Solo filas que existen en AMBAS tablas.
Ejemplo: solo líneas CON empresa registrada.
LEFT JOIN
Todas las filas de la tabla izquierda + matches.
Ejemplo: TODAS las empresas, tengan o no líneas.
RIGHT JOIN
Todas las filas de la tabla derecha + matches.
Raro — generalmente se reescribe como LEFT.
-- Empresas con su número de líneas activas SELECT e.ruc, e.razon_social, e.segmento, COUNT(l.id) AS total_lineas, SUM(CASE WHEN l.estado = 'ACTIVA' THEN 1 ELSE 0 END) AS lineas_activas FROM empresas e LEFT JOIN lineas l ON e.ruc = l.ruc_empresa GROUP BY e.ruc, e.razon_social, e.segmento HAVING COUNT(l.id) > 0 ORDER BY total_lineas DESC;
3️⃣ GROUP BY + Funciones de Agregación
-- Resumen de consumo por plan (para el dashboard del portal) SELECT plan_nombre, COUNT(*) AS total_lineas, AVG(consumo_mb) AS consumo_promedio_mb, MAX(consumo_mb) AS consumo_maximo_mb, SUM(consumo_mb) AS consumo_total_mb, COUNT(CASE WHEN consumo_mb > (limite_mb * 0.9) THEN 1 END) AS lineas_criticas FROM lineas WHERE estado = 'ACTIVA' GROUP BY plan_nombre HAVING COUNT(*) >= 5 -- solo planes con al menos 5 líneas ORDER BY consumo_promedio_mb DESC;

4️⃣ Subconsultas — Para validaciones de negocio
-- Empresas cuyo consumo promedio supera el 70% del plan -- (útil para identificar candidatos a upgrade de plan) SELECT ruc, razon_social FROM empresas WHERE ruc IN ( SELECT ruc_empresa FROM lineas WHERE estado = 'ACTIVA' GROUP BY ruc_empresa HAVING AVG(consumo_mb * 100.0 / limite_mb) > 70 );

🔷 Modelado de Datos — ERD y Normalización

El AF diseña el modelo conceptual y colabora con el DBA para el modelo físico. Debes poder dibujar un ERD básico en papel.

🎯 Pregunta típica: "Dibuja el modelo de datos básico para el portal de gestión de líneas de Comsatel. ¿Qué entidades identificas?"
📊 ERD — Portal de Líneas Corporativas

📐 Tipos de Relación

  • 1:1 — Un usuario tiene una sesión activa
  • 1:N — Una empresa tiene muchas líneas
  • N:M — Usuarios administran múltiples líneas (tabla intermedia)

📐 Normalización (lo mínimo)

  • 1FN: Sin grupos repetidos, cada celda = 1 valor
  • 2FN: Todo depende de la clave primaria completa
  • 3FN: Sin dependencias transitivas
  • Desnorm.: Para reportes/BI se acepta desnormalizar

🔀 API Gateway

Punto único de entrada para todas las APIs. Maneja: autenticación, rate limiting, logging, routing.

El AF lo menciona en: "El portal consume la API de consumo y la API de planes a través de un API Gateway centralizado."

⚡ Cache

Guarda respuestas frecuentes en memoria (Redis) para no ir a la BD cada vez.

Requisito: "Los datos de consumo se cachean 15 minutos. El catálogo de planes se cachea 24 horas."

📨 Queue / Cola de mensajes

Procesa tareas de forma asíncrona. Útil para notificaciones, emails, reportes grandes.

Requisito: "Las alertas de consumo se envían por cola (RabbitMQ/SQS) — el usuario las recibe en <5 min."

🔐 JWT / Tokens

JSON Web Token: estándar de autenticación stateless. El servidor emite un token firmado que el cliente envía en cada request.

Tienes experiencia con PCI-DSS y tokenización — aplica directamente.

⚠️ Lo que diferencia un AF Senior

  • Anticipa preguntas del equipo técnico
  • Sus stories no necesitan 3 rondas de aclaración
  • Sabe decir "eso no está en el alcance, lo ponemos en backlog" sin conflicto
  • Detecta cuando un dev interpreta mal un requisito antes de que se termine

✅ Waterfall vs Ágil — cuándo cada uno

  • Waterfall: Requisitos muy fijos, regulatorio (banca, gobierno), contratos de precio fijo
  • Ágil: Requisitos evolutivos, producto digital, equipo co-ubicado o coordinado
  • Híbrido: Fases predictivas (contrato, diseño) + ejecución ágil (sprints)
  • Comsatel: probablemente híbrido (contratos con cliente + desarrollo ágil interno)

🧪 Testing & UAT — Cómo validas que el sistema cumple los requisitos

El AF es responsable del UAT. Pero un Senior también entiende los otros tipos de prueba para colaborar mejor con el equipo de QA.

🎯 Pregunta típica: "¿Cómo escribes un caso de prueba? Dame un ejemplo para la funcionalidad de alerta de consumo."
🔺 Pirámide de Testing — Dónde actúa el AF
🟢 Unit Tests
Los escribe el desarrollador. Prueban funciones individuales. Rápidos, baratos, masivos. Ej: pytest, JUnit, xUnit.
🔵 Integración
Dev / QA. Valida que módulos trabajen juntos. Ej: llamada real a la API, inserción en BD. Herramientas: Postman, REST Assured.
🟡 E2E / Sistema
QA / AF. Simula el usuario real de inicio a fin. Costosos, lentos. Ej: Selenium, Cypress, prueba manual.
🔴 UAT ← TÚ
AF + Usuario Final. Valida que el sistema cumple los requisitos de negocio. Casos de prueba manuales. Sign-off formal.

🎯 Pregunta típica: "¿Tienes experiencia con Git? ¿Cómo manejas la documentación de requisitos en el repositorio?"
🌿 Git Flow — El flujo que usa el equipo de desarrollo

El AF interactúa con Git para: actualizar documentación en el repo, aprobar Pull Requests con cambios que afectan requisitos, revisar diffs de código cuando valida que una feature cumple los criterios.

⌨️ Flujo de trabajo Git del AF — Paso a Paso
1 🔽 Obtener el repositorio del proyecto solo la primera vez

Clona el repositorio en tu máquina. Solo se hace una vez por proyecto.

# Clonar el repositorio completo git clone https://github.com/empresa/portal-comsatel.git cd portal-comsatel
2 🔄 Actualizar tu copia local antes de empezar a trabajar

Sincroniza con los últimos cambios del equipo. Hazlo siempre antes de editar archivos.

# Traer cambios de la rama develop (la más actualizada) git pull origin develop # Ver el estado de tus archivos git status
3 🌿 Crear una rama para tu documentación nunca trabajes en main o develop directamente

Crea tu propia rama para no interferir con el trabajo del equipo de desarrollo.

# Crear rama y moverse a ella (-b = branch nuevo) git checkout -b docs/requisitos-modulo-lineas # Verificar en qué rama estás git branch
4 💾 Guardar tus cambios (commit) al terminar de editar

Primero agrega los archivos modificados al staging, luego guarda con un mensaje descriptivo.

# Agregar el archivo modificado git add docs/RF-001-consulta-consumo.md # Guardar con mensaje claro (convención: tipo: descripción) git commit -m "docs: actualiza criterios RF-001 según reunión 27-may"
5 📤 Subir al repositorio remoto para que el equipo vea tus cambios

Sube tu rama al servidor (GitHub/GitLab/Azure DevOps) y crea un Pull Request para revisión.

# Subir la rama al servidor git push origin docs/requisitos-modulo-lineas # En GitHub/GitLab: crea un Pull Request desde esta rama # → el equipo de dev revisa y aprueba los cambios
6 🔍 Inspeccionar el historial y cambios para auditoría y revisión

Revisar el historial para entender qué cambió, cuándo y por quién — útil en revisiones de sprint y auditorías.

# Ver historial resumido git log --oneline -10 # Ver exactamente qué cambió en un archivo git diff docs/RF-001.md # Ver quién cambió cada línea git blame docs/RF-001.md

✅ Pull Request — Rol del AF como revisor

  • Revisa que el código implementa los criterios de aceptación
  • Comenta discrepancias: "Este flujo no contempla el caso cuando el plan es 0MB"
  • Aprueba cuando el incremento cumple los requisitos
  • NO revisa calidad de código — eso es el tech lead

📁 Qué documenta el AF en el repo

  • /docs/requisitos/ — specs FR/NFR en Markdown
  • /docs/diagramas/ — UML, BPMN como imágenes
  • /docs/casos-prueba/ — casos de prueba UAT
  • /docs/decision-log/ — decisiones de diseño y su porqué
  • README.md — visión y contexto del proyecto
✅ Tu experiencia: Tienes Git/GitHub en tu CV y experiencia con Python en proyectos propios. Eso ya implica manejo del flujo básico. Menciona que en UPC y tus proyectos de análisis de datos usas Git para versionar scripts y documentación.

💬 Las 10 Preguntas del Jefe de Desarrollo

Preguntas reales que hace un Dev Lead en una entrevista con un AF Senior — con tus respuestas personalizadas basadas en tu CV.

🎯 Estrategia: Responde siempre con estructura: Contexto → Acción → Resultado. Menciona tecnologías por su nombre (SQL Server, Oracle, C#, Python, Bizagi). Cuantifica cuando puedas.
1
¿Cómo es tu proceso desde que un stakeholder te da un requerimiento hasta que el desarrollador empieza a codear?

Hay 5 etapas clave: (1) Levantamiento — entrevistas estructuradas y talleres con el stakeholder para entender el problema de negocio real, no solo lo que pide. (2) Análisis — modelo el proceso en BPMN con Bizagi para identificar el AS-IS y diseñar el TO-BE. (3) Especificación — escribo requisitos funcionales y no funcionales con criterios de aceptación medibles (Given/When/Then). (4) Revisión técnica — sesión con el equipo técnico para validar que es implementable y ajustar si hay restricciones. (5) Refinement — en el contexto Scrum, presento las historias en refinement para que el equipo estime y aclare dudas antes del sprint planning.

En Perurail, cuando el área comercial pidió "un sistema para gestionar reservas", mi primer paso fue modelar el proceso actual de reservas (15 pasos manuales) en Bizagi, identificar los 4 flujos críticos y priorizar el MVP. El equipo de desarrollo recibió specs tan detalladas que redujimos las dudas en desarrollo en un 60%.
2
Dame un ejemplo de un requisito mal especificado que causó problemas y cómo lo resolviste.

Los requisitos ambiguos más comunes son los que usan palabras como "rápido", "seguro" o "amigable" sin definición medible.

En un proyecto de AFP Profuturo, el requisito original decía "el sistema debe responder rápidamente". El equipo implementó sin criterio claro. Cuando el cliente probó con 200 afiliados concurrentes y la página tardaba 8 segundos, hubo conflicto. Aprendí que todo RNF de performance debe especificarse así: "El sistema debe responder en ≤2 segundos para el percentil 95 de requests con hasta 500 usuarios concurrentes, medido con JMeter en ambiente de staging". Desde entonces incluyo un RNF de performance firmado por el cliente en el kick-off.
3
¿Cómo colaboras con el equipo de desarrollo durante el sprint? ¿Cuánto tiempo del desarrollador consumes?

El AF debe estar disponible pero no ser una interrupción constante. La regla que sigo: si una duda del dev tarda menos de 5 minutos en aclarar, la respondo inmediatamente. Si es compleja, agendo una sesión corta (30 min) con el arquitecto o tech lead incluido.

En la práctica, mantengo un canal de Slack/Teams dedicado al proyecto donde los devs pueden poner dudas con contexto. Respondo en máximo 2 horas en horario laboral. Adicionalmente, en el daily me aseguro de preguntar si hay algún requisito que esté siendo interpretado diferente. En proyectos Scrum también hago "desk check" informal a mitad del sprint — reviso el trabajo en progreso antes de que esté terminado, para atrapar malentendidos temprano.
4
¿Qué haces cuando un desarrollador te dice que un requisito es técnicamente imposible?

Primero escucho y entiendo la restricción técnica. Luego analizo si el objetivo de negocio se puede cumplir de otra forma. Hay una diferencia entre "no se puede hacer así" y "no se puede hacer".

En Oncosalud, el dev dijo que no podíamos procesar pagos en tiempo real sin depender del gateway externo (que tenía SLA de 3 segundos). El requisito original pedía confirmación "instantánea". Analizamos el flujo y propuse una solución: confirmación optimista inmediata al usuario + procesamiento asíncrono en background con notificación por email si fallaba. El cliente aceptó porque el objetivo real era "el usuario no espera en pantalla", no necesariamente que el proceso termine en tiempo real. Esa solución se implementó y redujo los timeouts percibidos por el usuario a cero.
5
¿Tienes experiencia con integraciones entre sistemas? ¿Cómo las documentas?

Las integraciones son el punto más delicado en análisis porque involucran dos sistemas, dos equipos y a veces dos empresas. Mi documentación de integración siempre incluye: el contrato de la API (endpoints, request/response, errores), el diagrama de secuencia con los flujos exitosos y de error, y un acuerdo de SLA entre sistemas.

En AFP Profuturo trabajé con la integración entre el sistema de afiliados y la plataforma de tokenización de pagos (PCI-DSS). Documenté el flujo completo con diagrama de secuencia: usuario → frontend → backend AFP → gateway tokenización → banco. Para cada llamada especifiqué el timeout esperado, el comportamiento en caso de error (retry, fallback, mensaje al usuario) y los controles de auditoría requeridos por PCI-DSS. Esta documentación sirvió también para el equipo de QA para diseñar los casos de prueba de integración.
6
¿Cómo manejas el scope creep — cuando el cliente pide cambios en mitad del sprint?

Con respeto pero con firmeza. El scope creep es la principal amenaza a la velocidad del equipo. El proceso que sigo: registro el nuevo pedido en el backlog, evalúo su prioridad con el PO, y si es urgente negocio el intercambio (saca algo del sprint o espera al siguiente).

En UPC, donde coordinaba proyectos académicos con múltiples stakeholders, la frase que aprendí a usar es: "Eso es una excelente mejora, lo registramos en el backlog. Si es prioritario, podemos verlo en el próximo sprint — ¿qué sería lo menos crítico de sacar del sprint actual para incluirlo?". Eso involucra al cliente en el trade-off en lugar de simplemente decirle "no". Funciona 9 de cada 10 veces.
7
¿Qué experiencia tienes con bases de datos? ¿Puedes hacer consultas SQL?

Sí, tengo experiencia con SQL Server y Oracle. Escribo consultas para validar datos, verificar que los reportes muestren los valores correctos y crear consultas de análisis para Power BI y MicroStrategy. No soy DBA, pero puedo leer y escribir queries de complejidad media — JOINs, GROUP BY, subconsultas.

En AFP Profuturo validaba los reportes de fondos de pensiones directamente contra la BD Oracle. Por ejemplo, cuando el reporte de MicroStrategy mostraba un número diferente al que el actuario calculaba manualmente, escribía la consulta equivalente en SQL para encontrar la discrepancia. En Python con pandas hacía el mismo análisis pero para conjuntos de datos grandes que SQL tardaba en procesar.
8
¿Cómo validas que lo que entregó el equipo de desarrollo cumple los requisitos?

El proceso de UAT tiene 3 niveles: (1) Desk check informal a mitad del sprint — reviso el trabajo en progreso antes de que esté terminado. (2) Pruebas formales contra los casos de prueba documentados en el sprint review. (3) Pruebas de regresión — me aseguro que lo nuevo no rompe lo anterior.

Tengo una práctica: antes del sprint review, paso 2 horas en ambiente de QA ejecutando los casos de prueba de las historias del sprint. Así llego al sprint review con un estado claro: qué pasa, qué falla. Si hay una historia que falla un criterio, la marco como no aceptada con el caso de prueba fallido documentado — no con una queja genérica. Eso ayuda al dev a entender exactamente qué corregir sin debates.
9
¿Has trabajado con equipos de desarrollo remotos o distribuidos? ¿Cómo te organizas?

Sí, en varios proyectos he coordinado con equipos distribuidos en diferentes ciudades o países. Las claves: documentación escrita clara (no solo verbal), uso disciplinado de herramientas (Jira, Confluence, Slack), horario de reuniones con ventana de solapamiento y decisiones siempre documentadas en ticket o acta.

En Belmond Perurail coordinaba con equipos en Lima y Cusco. La regla que establecimos: ninguna decisión de diseño o cambio de alcance se tomaba en una llamada sin quedar documentado en el ticket de Jira. Eso evitaba el "yo creí que habíamos dicho X". También estandarizamos el formato de user story para que cualquier dev pudiera retomar una historia sin necesitar una sesión de explicación.
10
¿Por qué quieres trabajar en Comsatel y qué aportarías al equipo de desarrollo?

Esta pregunta cierra la entrevista — es tu momento de diferenciarte.

"Comsatel opera en un sector que conozco desde el lado del cliente corporativo — he gestionado proyectos de TI donde el proveedor de telecomunicaciones era un aliado crítico. Eso me da perspectiva real del dolor que tienen los administradores corporativos cuando no pueden autogestionar sus líneas.

Lo que aportaría al equipo de desarrollo es un puente sólido entre el negocio y el código: requisitos tan claros que el desarrollador pueda arrancar sin necesitar 3 reuniones de aclaración, validaciones técnicas que detecten inconsistencias antes de que lleguen al dev, y 28 años de experiencia en sectores regulados (banca, salud, gobierno) que me permiten anticipar los casos borde que el cliente no menciona pero sí espera que el sistema maneje."
✅ Tip final para mañana: Lleva 2 ejemplos concretos memorizados: uno de un requisito bien especificado que aceleró el desarrollo, y uno de un bug que detectaste en UAT que habría costado mucho más tarde. Esos dos ejemplos responden el 70% de las preguntas de un Dev Lead.
