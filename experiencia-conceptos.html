UPC
Trabajo 1 de 5 · Más reciente
Project Manager / Scrum Master
Universidad Peruana de Ciencias Aplicadas — IP InfoOut
🎓 Educación
Dic 2021 — Jul 2023
▼
Gestión de 25 requerimientos funcionales en metodología ágil con 2 sprints paralelos. Lideré 3 proyectos PMI: WeTalk continuidad, GEMA evaluaciones y nueva arquitectura WeTalk. Presupuesto CAPEX/OPEX mayor a USD 5 MM.
🔥 Conceptos del repaso aplicados directamente
🔄
SDLC & Agile — Scrum
Rol de Scrum Master activo. Facilité Sprint Planning, Daily, Refinement, Review y Retrospectiva. 2 sprints paralelos = gestión simultánea de 2 equipos.
🏗
PMI / PMBOK
3 proyectos con ciclo completo: Project Charter, WBS, cronograma, gestión de cambios y cierre formal. Presupuesto de USD 5MM+ con gestión CAPEX/OPEX.
💰
Análisis Financiero — CAPEX/OPEX
Gestión real de presupuesto CAPEX/OPEX superior a USD 5 millones. Justificación de inversiones ante stakeholders y reportes al comité directivo.
📋
Requisitos Funcionales
Levantamiento y especificación de 25 requerimientos funcionales. Definition of Ready aplicado antes de cada Sprint Planning.
📋
Matriz de Trazabilidad
Seguimiento de los 25 requerimientos desde levantamiento hasta pruebas y aceptación del cliente interno (UPC).
⚠️
Matriz de Riesgos
Gestión de riesgos de proyectos de alta envergadura (USD 5MM). Riesgos técnicos, de adopción y de stakeholders mapeados por proyecto.
🎛
BSC / OKRs
Reporte de KPIs de avance al comité directivo de UPC. Métricas de proyecto alineadas a los objetivos estratégicos del área de tecnología.
🏢
Organigrama del Equipo Ágil
Operé como Scrum Master: coordiné PO (cliente interno), equipo de desarrollo e infraestructura. Gestión del equipo ágil en entorno universitario.
Frase de entrevista
"En UPC gestioné 3 proyectos PMI en paralelo con metodología ágil, incluyendo 2 sprints simultáneos. Manejé un presupuesto de más de USD 5 millones CAPEX/OPEX y apliqué Scrum como Scrum Master certificado. Eso me dio la base para entender qué necesita el equipo de desarrollo del analista funcional: historias claras, criterios sin ambigüedad y presencia activa en las ceremonias."
PR
Trabajo 2 de 5 · Rol PO directo
Analista Funcional / Product Owner
Belmond Perurail — MDP Consulting
🚂 Turismo / Comercial
Jun 2020 — May 2021
▼
AS-IS / TO-BE de requerimientos comerciales del sistema de reservas y experiencia del viajero. Diseño de prototipos, especificación de casos de uso, creación de casos de prueba y backlog del producto.
🔥 Conceptos del repaso aplicados directamente
📦
Épicas & Product Backlog
Rol de PO directo: gestión del backlog priorizado del sistema de reservas. Épicas como "Proceso de Compra de Ticket", "Historial de Reservas", "Gestión de Itinerarios".
🔄
BPM — AS-IS / TO-BE
Modelado BPMN del proceso de reservas turísticas. Diagramas AS-IS del proceso actual vs. TO-BE con las mejoras propuestas. Swimlanes por actor (cliente, agente, sistema).
📐
UML — Casos de Uso
Especificación formal de casos de uso del sistema de reservas. Actores: viajero, agente, administrador. Flujo normal + flujos alternativos + excepciones.
📝
User Stories + Criterios de Aceptación
Escritura de historias en formato As a / I want / So that. Criterios Given/When/Then para cada historia del backlog del sistema de reservas de Perurail.
🧪
Testing & UAT
Diseño de casos de prueba para validar el sistema de reservas. UAT con usuarios finales (agentes de viaje) verificando criterios de aceptación definidos.
🎯
MoSCoW — Priorización
Priorización del backlog: proceso de compra (Must), historial (Should), exportar PDF (Could), gamificación viajero frecuente (Won't this version).
🚀
MVP
Definición del mínimo viable del sistema comercial: solo las funciones críticas para el proceso de venta directa. Resto diferido para versiones siguientes.
🗓
Roadmap del Producto
Plan de entregas por trimestre para el sistema de reservas. Visión de producto alineada a los objetivos comerciales de Belmond Perurail.
Frase de entrevista
"En Belmond Perurail ejercí como Product Owner directo del sistema de reservas turísticas. Gestioné el backlog priorizado con MoSCoW, modelé los procesos AS-IS/TO-BE con BPMN, escribí historias de usuario con criterios de aceptación Given/When/Then, y diseñé los casos de prueba para el UAT con los agentes de viaje. Ese rol me demostró que el PO necesita dominar tanto el negocio como el lenguaje del equipo técnico."
OS
Trabajo 3 de 5
Jefe de Proyecto
Oncosalud — Evol / MDP Consulting
🏥 Salud
Nov 2018 — May 2020
▼
Proyecto PCI-DSS / Certificación VISA — implementación de seguridad, enmascaramiento y tokenización de datos de pago. Gestión de presupuesto CAPEX/OPEX con reportes al comité directivo del proyecto.
🔥 Conceptos del repaso aplicados directamente
🏗
PMI / PMBOK — Gestión de Proyecto
Gestión completa del proyecto PCI-DSS: Project Charter, WBS de seguridad, gestión de proveedores externos, control de cambios y cierre con auditoría VISA.
⚠️
Matriz de Riesgos
PCI-DSS es 100% gestión de riesgos de seguridad. Cada control del estándar mapeado como riesgo: probabilidad de brecha, impacto regulatorio (multa VISA), plan de mitigación técnica.
🔌
APIs REST — Tokenización de Pagos
Tokenización = integración de API de pasarela de pago. Especificación de endpoints POST /tokenize y PUT /payment con esquemas de seguridad (HTTPS, OAuth, datos enmascarados).
💰
Análisis Financiero — CAPEX/OPEX
Presupuesto de seguridad justificado: comparativa costo de implementación PCI-DSS vs. costo potencial de una brecha (multas VISA + daño reputacional).
🔷
Modelo de Datos — Enmascaramiento
El enmascaramiento de datos de tarjeta requiere rediseñar el modelo de datos: qué campos se almacenan, cuáles se tokenizán, cuáles se enmascaran en la UI.
📋
Requisitos Funcionales y No Funcionales
RNF de seguridad críticos: cifrado AES-256, respuesta en <200ms para tokenización, disponibilidad 99.9%, logs de auditoría de cada transacción. Todos medibles y verificables.
🎛
BSC / OKRs — Reporte al Comité
Reportes ejecutivos al comité directivo de Oncosalud con dashboards de avance del proyecto: % de controles PCI-DSS implementados, riesgos mitigados, presupuesto ejecutado.
📈
KPIs del Proyecto
KPI principal: 100% de controles PCI-DSS aprobados en auditoría VISA. KPI secundario: cero chargebacks por fraude tras implementación de tokenización.
Frase de entrevista
"En Oncosalud lideré el proyecto de certificación PCI-DSS con VISA, que implicó tokenización de pagos, enmascaramiento de datos sensibles y gestión de riesgos de seguridad con impacto regulatorio directo. Aprendí a especificar requisitos no funcionales que no se pueden negociar — velocidad, cifrado, trazabilidad — y a justificar el presupuesto de seguridad en términos de ROI frente al costo de una brecha."
AFP
Trabajo 4 de 5
Jefe de Proyecto / Analista Funcional
AFP Profuturo — MDP Consulting
🏦 Banca / Finanzas
Sep 2013 — May 2014
▼
Business Intelligence en Oracle — implementación de Data Warehouse y reportes con MicroStrategy. Diagramas UML del sistema. Cumplimiento de reglas SBS (Superintendencia de Banca) y Sunat.
🔥 Conceptos del repaso aplicados directamente
📐
UML — Diagramas de Sistema
Especificación formal del sistema BI con UML: diagramas de casos de uso para los reportes, diagramas de secuencia para los procesos ETL, diagrama de clases del modelo de datos del DW.
🗄
SQL — Data Warehouse Oracle
Consultas SQL complejas sobre Oracle DW: JOINs de múltiples tablas dimensionales, GROUP BY con HAVING para reportes SBS, subconsultas para cálculos de indicadores de AFP.
🔷
Modelo de Datos — Data Warehouse
Diseño del modelo dimensional (estrella/copo de nieve) para el DW de AFP: hechos (transacciones de fondo), dimensiones (afiliado, fondo, período, agencia).
💰
Análisis Financiero — Sector AFP
Dominio de indicadores financieros específicos de AFP: rentabilidad del fondo, volatilidad, valor cuota, proyección de pensión. Reglas SBS que rigen los reportes regulatorios.
📋
Requisitos Funcionales (sector regulado)
Especificación de requisitos bajo marco regulatorio SBS/Sunat. Requisitos no negociables: formatos exactos, plazos de entrega de reportes, trazabilidad de datos para auditoría.
🛠
Herramientas de BI y Analytics
MicroStrategy como herramienta de reporte y dashboards. Equivalente moderno: Power BI / Tableau. La experiencia es directamente aplicable a los dashboards analíticos del portal TI Corp.
Frase de entrevista
"En AFP Profuturo trabajé con Business Intelligence sobre Oracle DW en un entorno altamente regulado por la SBS. Usé UML para especificar el sistema, SQL complejo para construir los reportes, y aprendí a manejar requisitos no negociables en sectores regulados: cuando la SBS define el formato de un reporte, no hay margen para negociar. Esa experiencia me enseñó que los requisitos no funcionales de cumplimiento legal son tan críticos como los funcionales."
CB
Trabajo 5 de 5
Analista de Procesos Técnicos
Banco Citibank del Perú
🏦 Banca
Jun 2010 — May 2011
▼
Proyecto Web Paylink Back End — sistema de transferencias interbancarias B2B. Diagramas UML, metodología RUP, diseño de prototipos de interfaz. Integración con sistemas bancarios core.
🔥 Conceptos del repaso aplicados directamente
📐
UML — Proyecto Bancario B2B
Diagramas UML completos para Paylink: casos de uso del flujo de pago B2B, diagramas de secuencia entre cliente-backend-banco destino, diagrama de estados de la transacción (Pendiente → Procesando → Confirmado → Rechazado).
🔌
APIs REST / Servicios Web B2B
Paylink Back End = servicios web de transferencias. Especificación de endpoints de pago B2B: autenticación, validación del destinatario, ejecución de transferencia, confirmación y manejo de errores bancarios.
🔄
BPM — Flujo de Transferencias Bancarias
Modelado del proceso de transferencia interbancaria con swimlanes: empresa originante → Citibank → sistema SWIFT/LBTR → banco destino. Identificación de puntos de falla y planes de contingencia.
🔷
Modelo de Datos — Sistema Bancario
Entidades del sistema bancario: Empresa, Cuenta, Transacción, Beneficiario, Banco. Relaciones de alto volumen (millones de transacciones). Normalización para garantizar integridad financiera.
📋
Requisitos Funcionales — RUP
Metodología RUP (precursor de los métodos ágiles actuales): levantamiento formal de requerimientos, especificación de casos de uso detallados, revisión iterativa con el equipo técnico.
🏗
Arquitectura — Sistema Bancario N-Tier
Sistema bancario B2B en arquitectura de N capas: interfaz empresarial, backend Paylink, middleware de integración, core bancario. Comprensión de arquitecturas complejas de alta disponibilidad.
Frase de entrevista
"En el Banco Citibank especifiqué un sistema de transferencias interbancarias B2B con UML completo, modelé el flujo con swimlanes mostrando la interacción entre 4 actores, y definí los servicios web de pago con todos sus estados posibles. En banca no hay margen para ambigüedad: un requerimiento mal especificado puede resultar en una pérdida financiera real. Esa presión me formó como analista funcional riguroso."
